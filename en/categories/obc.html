OBC — On-Board Computer & Embedded Processor

An On-Board Computer (OBC) does one thing: execute code. It's a brain. Nothing more. What differentiates products is what you plug into it (interfaces), what runs on it (software, OS, certification) and which processor type it embeds. Everything else — hardening, redundancy, housing — are domain constraints that come on top.

Types · Interfaces · Software

Three questions to choose an OBC

An OBC is a brain. To choose one, you need to answer three questions: what processor type is needed, what interfaces must it expose to talk to subsystems, and what software (OS, certification) must run on it. Everything else — housing, radiation hardening, redundancy — is a domain constraint that comes on top.

Processor type
🖥️
CPU / MCU — the generalist
ARM Cortex-M/A, industrial x86, LEON3/4 (space), PowerPC. Executes sequential software, handles interrupts, drives peripherals. The default choice when processing is software-based and data throughput is moderate.
⚙️
FPGA — deterministic parallelism
Xilinx/AMD, Intel/Altera, Microsemi (rad-hard). Reconfigurable logic that executes operations in parallel with fixed, predictable latency. Chosen for radar synthesis, image processing, high-frequency motor control, or when timing must be guaranteed to the nanosecond.
🤖
GPU / NPU — the AI engine
NVIDIA Jetson, Hailo, Qualcomm SA, dedicated inference processors. Massively parallel computation optimized for neural networks and sensor fusion. Essential for autonomous perception, embedded video processing, GPS-denied navigation.
🔀
Hybrid SoC CPU + FPGA
Xilinx Zynq, Intel SoC FPGA. A CPU manages the OS and application software; the FPGA handles real-time data streams in parallel. Best of both worlds: software flexibility + hardware determinism, on a single chip.
Interfaces
📡
System communication bus
SpaceWire (ESA/space), MIL-STD-1553 (defense/aero), ARINC 429 (civil avionics), CAN FD (automotive/industry), Ethernet TSN (industry/mobility). The chosen bus locks in the ecosystem: each domain has its standards, and its equipment often speaks only one protocol.
🔌
Physical I/O & sensors
GPIO, ADC/DAC, UART, SPI, I²C, RS-422, PWM. Low-level interfaces connecting the OBC directly to sensors (IMU, temperature, pressure) and actuators. The number and type of available I/O pins determine what can be connected without an expansion board.
💾
Memory — on-board or off-board
OBCs can integrate memory directly on the board (soldered RAM, Flash, MRAM, EEPROM) for compactness and reliability, or expose interfaces to off-board mass storage (NVMe SSD, eMMC, SD, external NAND). The choice depends on the data volume, mass constraints, and whether storage needs to be replaced or expanded in operation. See the embedded memory page →
🛰️
Telecommand / telemetry interfaces
CCSDS (space), MAVLink (drones), NMEA (GPS), SNMP (network). Application protocols that structure exchanges between the OBC and the operator or ground segment. Distinct from physical buses: the same SpaceWire link can carry CCSDS or a proprietary protocol.
Software & OS
⏱️
OS & RTOS
FreeRTOS, RTEMS, VxWorks, LynxOS, Linux RT, AUTOSAR Adaptive, Zephyr. The OS choice determines timing guarantees, library ecosystem, and ease of certification. Bare-metal for the simplest or most constrained applications; RTOS as soon as there are multiple concurrent tasks.
🛡️
Software certification
DO-178C DAL-A (avionics), ISO 26262 ASIL-D (automotive), ECSS-E-ST-40 (space), IEC 61508 SIL-3 (industry). Certification is not a software option — it's an entire development process that constrains architecture, testing and traceability. Often represents 40 to 70% of the total cost of a critical project.
🧩
Middleware & application framework
ARINC 653 (avionics partitioning), AUTOSAR Classic (automotive ECU), ROS 2 (robotics), PX4/ArduPilot (drones), TASTE/POHIC (ESA space). Layer between the OS and business software that standardizes task, message and resource management. A certified middleware simplifies qualification of the application software running above it.

Application domains

Same tool, different options

The base OBC doesn't change. It's the domain constraints that dictate which options the manufacturer integrates, at what quality level, and under what certification.

Space — the OBC becomes the satellite brain

Satellite · CubeSat · Launcher · Probe
  • All options enabled, at maximum quality level
  • Rad-hard LEON3/4 processor (Cobham Gaisler) — European space industry standard
  • EDAC on all memories — radiation causes bit-flips
  • FPGA configuration scrubbing — SEUs corrupt the configuration bitstream
  • Hot or cold redundancy — an in-orbit failure is permanent
  • SpaceWire as main bus — ESA standard protocol for space subsystems
  • Minimized mass — every gram has a launch cost

Defense & Aero — DAL certification first

Aircraft · Drone · Helicopter · Missile · Radar
  • Priority options: certification + redundancy + aero interfaces
  • Software developed per DO-178C DAL-A — every line of code is traceable and tested
  • Hardware compliant with DO-254 DAL-A — mandatory safety analysis and design review
  • MIL-STD-1553 and ARINC 429 as main buses — certified aeronautical protocols
  • Dual-dual redundancy — two active channels, permanent cross-voting
  • MIL-STD-810 hardening — vibration, shock, humidity, altitude
  • MIL-SPEC housing + MIL-DTL-38999 connectors — aero-qualified connectors

Industry — versatility and connectivity

Automation · Energy · Robotics · IIoT
  • Priority options: connectivity + standard OS + longevity
  • Industrial x86 or ARM with Linux or Windows IoT — broad development ecosystem
  • Ethernet, USB, RS-232/485, CAN, Profibus, EtherCAT — integration with existing SCADA
  • Industrial grade: −40/+85 °C, anti-vibration, anti-condensation
  • 10–15 year availability guaranteed — long industrial lifecycle
  • PCIe, PC/104, COM Express, DIN Rail formats per integration type
  • Standard CE / UL certification — no specific safety development unless SIL required

Mobility & EV — functional safety and embedded AI

Electric vehicle · Drone · Rail · Autonomous mobility
  • Priority options: ISO 26262 + CAN FD + AI processing
  • ECU (Electronic Control Unit) or domain controller — centralized or distributed architecture
  • ISO 26262 ASIL-D for safety functions (braking, steering, propulsion)
  • AUTOSAR Classic or Adaptive as middleware — portability and certification
  • CAN FD + Ethernet TSN — network determinism for embedded real-time systems
  • Embedded NPU / GPU for ADAS / autonomous driving inference — Level 2+ to 4
  • AEC-Q100 components qualified for vehicle lifetime (−40/+150 °C, 15 years)
